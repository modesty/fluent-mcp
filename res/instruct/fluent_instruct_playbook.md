# Instructions for Fluent PlaybookDefinition API
Always reference the PlaybookDefinition API specifications for more details.
1. Import `PlaybookDefinition`, `wfa`, `PlaybookTriggerTypes`, and `ActivityDefinitions` from `@servicenow/sdk/automation`. Import Column types (`ReferenceColumn`, `IntegerColumn`, `StringColumn`, etc.) for inputs/outputs from `@servicenow/sdk/core`.
2. Use a Playbook to model a **guided, record-driven multi-step process** (lanes of activities a fulfiller works through). It is distinct from a Flow: playbooks are interactive and operate on a parent record.
3. Call `PlaybookDefinition(config, triggers, body)` with **three arguments**. `config` holds top-level properties plus declarative `inputs`/`outputs`; `triggers` is `{ triggers: [...] }`; `body` is `{ lanes: (params) => ({...}) }`.
4. In `config`, `$id` (use `Now.ID['...']`) and `label` are mandatory. Set `parentTable` to the table the playbook runs on — this auto-creates a `parent_record` input exposed as `params.parentRecord` (dot-walkable to fields). Treat `name` as stable identity: don't change it after deploy, or the platform creates a new record instead of updating.
5. The `triggers` array is **required even when empty** — pass `{ triggers: [] }` for a playbook with no triggers. Build each trigger with `wfa.playbook.trigger(triggerType, config, triggerInputs, playbookInputs?)`. Choose `triggerType` from `PlaybookTriggerTypes` (`RecordCreate`, `RecordUpdate`, `RecordCreateOrUpdate`, `Scheduled`).
6. Trigger inputs differ by type: record-based triggers take `{ table, condition?, runTriggerOnExtendedTables? }`; scheduled triggers take `{ table, condition?, limit (1-1000), startDateAndTime, timeZone? }` plus schedule-type fields. Use the optional 4th `playbookInputs` arg only when the playbook declares inputs or the trigger table differs from `parentTable`; wrap record references in `wfa.playbook.dataPill(trigger.current...)` and use plain values for literals.
7. `body.lanes` **must be a callback** `(params) => ({...})` — the build transformer reads lane/activity keys statically from the arrow-function body, not from a plain object. Build lanes with `wfa.playbook.lane({ config, activities })`, where `config` is a plain `LaneConfig` and `activities` is another `(params) => ({...})` callback. Inside `activities`, use `const` bindings and an explicit-key `return { name: name }` so keys are statically extractable.
8. Every lane and activity config requires `$id`, `label`, `order`, `startRule`, and `restartRule`. Set execution order with `startRule`: `wfa.playbook.run.Immediately()` for no dependencies, or `wfa.playbook.run.After(...deps)` (varargs, not an array) to wait for activities, lanes, or decision branches. `order` controls only visual layout. `restartRule` is `'RUN_ALWAYS'`, `'RUN_ONLY_ONCE'`, or `'RUN_ONLY_ON_RESTART'`.
9. Create activities with `wfa.playbook.activity(definition, config, inputs?, experienceProperties?)` using definitions from `ActivityDefinitions.Core.*` (e.g. `UpdateRecord`, `CreateNewRecord`, `SendEmail`, `Instruction`, `Decision`). Pass automation inputs in the 3rd arg and UI configuration in the 4th. Reference runtime data with `wfa.playbook.dataPill(...)` and field templates with `TemplateValue({...})`.
10. For branching, use `ActivityDefinitions.Core.Decision` with inputs `{ type: 'match_first' | 'match_all', branches: [...] }`. Each branch needs `id`, `label`, and (except the `else` branch) a `condition`. The `else` branch must be **last** with `id: 'else'`, `label: 'Else'`, and no condition. Depend on a branch via `wfa.playbook.run.After(decision.branches.<id>)`.
11. `outputs` are declarative schema only — you cannot assign or consume them from the Fluent DSL yet; wire them via the "Set Playbook Outputs" activity in Playbook Designer.
12. Remember: deploying a playbook does **not** update already-running instances. Open Playbook Designer and re-activate the playbook to apply changes at runtime (the build output logs this reminder).
13. **SDK v4.11.0** — argument 2's type was renamed from `PlaybookTriggerDeclaration` to `PlaybookDependentConfig<I, P, E>`; the old name no longer exists in the package. If you import that type by name, update it. Its shape now depends on argument 1 — the `inputs` schema, `parentTable`, and `executionType` all flow into it — and it carries `permissions` in addition to `triggers`.
14. **SDK v4.11.0** — `executionType` widened to `'record_driven' | 'on_demand'`. Choose `'on_demand'` (standalone) only when the playbook is started explicitly rather than by a record trigger, and know that **six things change at once**: omit `triggers` entirely (not even `[]`), do not set `parentTable`, do not reference `params.parentRecord` anywhere in `lanes` or `permissions`, do not set the launcher record-form fields, `allowAsNested` may finally be `true`, and **at least one permission set must grant `launch: true`** — that last one fails the build even when `permissions` is omitted altogether. All six are enforced as both a type error and a build diagnostic.
15. **SDK v4.11.0** — the launcher fields are counterintuitive, so read this before using them: `launcherShowRecordForm`, `launcherRecordFormView`, and `launcherTemplateFields` are **forbidden** on an `'on_demand'` playbook despite being called "on-demand launcher" configuration. They pre-populate a `parentTable` record, and `parentTable` is itself forbidden there — so they belong to launching a **record-driven** playbook on demand. Only `launcherTitle`, `launcherDescription`, and `launcherInputs` are legal on a standalone playbook.
16. **SDK v4.11.0** — launcher field rules: set `launcherShowRecordForm: true` **first**, because using either of the other two record-form fields without it is a build error. `launcherRecordFormView` stores the view's **sys_id**, not its display name — `'Default view'` is a special-case string that works as-is, but any other view must be passed by real sys_id (or a typed `Record<'sys_ui_view'>`); the SDK cannot resolve a display name or verify the view exists. In `launcherInputs`, pass a **string** for every non-reference input including booleans and integers (`'true'`, `'3'`) — a raw literal does not compile — and remember it only changes what the launcher *displays*, never the input's own `default`.
17. **SDK v4.11.0** — permissions come in two flavours that are **not** interchangeable. Playbook-level `permissions` (argument 2) is a **callback** `(params) => ({...})` so pills can reach `params.parentRecord`; lane-level `permissions` (on `LaneConfig`) is a **plain object**. Playbook flags are `view`, `launch`, `laneAddOptionalActivity`, `restart`, `laneRestart`, `activityRestart`, `cancel`; lane flags are the reduced set `view`, `addOptionalActivity`, `restart`, `activityRestart`.
18. **SDK v4.11.0** — `view` behaves differently at the two levels, and this is the easiest permission mistake to make. On a **playbook** permission set `view` is **required and gates every other flag** — another flag without `view: true` on that same set is a build error and grants nothing. On a **lane** permission set all four flags are **independent and optional**; `view` gates nothing. Group each reference under the right kind (`users`/`userGroups`/`roles`/`userCriterias`) and list each reference once.
19. **SDK v4.11.0** — reference forms differ by level too. At the playbook level `user`/`userGroup` are normally data pills, and a bare sys_id string is only valid when `executionType` is not `'record_driven'`. At the lane level `user`/`userGroup` must be data pills; only `role` and `userCriteria` accept a bare sys_id string.
20. **SDK v4.11.0** — use `wfa.playbook.activityRef(Now.ID['x'])` inside `wfa.playbook.dataPill()` to reference an activity's **outputs** from somewhere that cannot see the activity variable — which in practice means playbook and lane `permissions`. It matches by `$id` against any activity in the playbook, so the activity need not be in lexical scope. Only outputs are referenceable; prefer the ordinary local or lane variable wherever it is visible.
21. **SDK v4.11.0** — optional activities: pass `startRule: wfa.playbook.run.Manually()` for an activity a user starts by hand at runtime (Playbook Designer calls it "optional"). Its config is narrower — omit `order`, `conditionToRun`, and `startWithDelay`, and pin `restartRule: 'RUN_ONLY_ONCE'`. **The call returns a `ManualActivityReference` with no outputs, deliberately outside the `Dependency` union**: because an optional activity may never run, nothing may reference its outputs or wait on it with `run.After()`. Do not design a dependency chain through one.
22. **SDK v4.11.0** — `ActivityDefinitions.Core.SetPlaybookOutputs` writes the playbook's own declared `outputs`. Its single authored input is `playbook_outputs`, a `TemplateValue` keyed by the playbook's `outputs` names. Do not attempt to set `playbook_outputs_var_table_name` — the plugin derives it from the containing playbook and it is deliberately hidden from the DSL.
23. **SDK v4.11.0** — AI-agent activity configuration is available **only** on definitions declaring `enableAiAgent: 'on'`, which in this release means exactly four OOB definitions: `RecordForm`, `AutocompletingRecordForm`, `NewRecordForm`, and `EmailForm` (`AutocompletingRecordForm` exposes a reduced field set). Setting any AI field on any other definition is a TypeScript error. `aiAgentObjective` is required once `enableAiAgent` is true — omitting it or passing `''` is a build error. `aiAgentExecutionMode: 'on'` (Autonomous) is a build error unless the definition itself declares it, and `aiAgentObjAdditionalDetail` set while the mode is not `'on'` is a warning whose value is silently discarded. The SDK validates none of the platform prerequisites: the `sn_genai_platform` store app must be installed and `sn_pa_designer.enable_agentic_playbooks` must be `true`, or the configuration has no runtime effect.
24. **SDK v4.11.0** — `schemaVersion` is now a public property rather than internal, and its ceiling is **instance-dependent**: Australia and older releases cap at 3, Brazil and newer also accept 4. Set `4` explicitly only after confirming the target instance's `com.glide.pad.core.model.maxSupportedSchemaVersion` system property — do not infer the ceiling from the release name. Leave it unset to take Fluent's safe fallback.
25. **SDK v4.11.0** — dependent record inputs are now type-checked: `UpdateRecord` and `CreateNewRecord` preserve `rawInputs`, so a `record` pill must match the table named in the sibling `table_name` input (a `sys_user` `UpdateRecord` rejects an `incident` pill at compile time), and `RecordForm`'s `associated_record` is checked against `associated_table` the same way. Keep the table and the pill in agreement rather than casting past the error. `SendEmail` also gained `to_email_address`, `cc_email_address`, and `bcc_email_address` inputs.
